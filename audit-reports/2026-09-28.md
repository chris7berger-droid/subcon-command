## Top 3 Urgent

1. **B-archive-grant-anon (HIGH — third audit cycle)** — `sql/history_locker_phase1.sql:119` still ships `GRANT ALL ON ALL TABLES IN SCHEMA archive TO anon, authenticated;` plus `ALTER DEFAULT PRIVILEGES … TO anon`. Anon holds full DML on `archive.import_batches` + `archive.legacy_records` (raw legacy PII + dollar amounts). Today's protection rests entirely on `archive.get_user_tenant_id()` returning NULL for anon → predicate NULL → rows denied; RLS policies at :86-109 also lack `TO authenticated`, defaulting to PUBLIC, and cover only SELECT/INSERT/DELETE while the GRANT includes UPDATE. Fix: `GRANT SELECT,INSERT,DELETE … TO authenticated` only; add `TO authenticated` on every policy; `ALTER DEFAULT PRIVILEGES … TO authenticated` only.

2. **Client-side money-writes on the DMS-1 / HistoryLocker / Multi-GC surface with NO role gate — 16 handlers, all HIGH.** ProposalDetail's five handlers (`deleteWtc:304`, `toggleWtcLock:312`, `handleDelete:564`, `handlePullBack:587`, `commitSendToSchedule:684`, `handleInternalApprove:956`, `ArchiveProposalPanel.handleSave:1687`), Invoices' six (`handleCreate:317`, `handleDelete:2097`, `handleSaveEdit:2143`, `handleBillRetention:2302`, `handlePullBack:2376`, `handleVoidConfirm:2463`), WTCCalculator's two (`handleSave:2269`, `handleLock:2360`), MobilizationsEditor (`persist:206`), PayAppDetailModal (`handleDeletePayApp:264`), CallLogDetail (`handleDelete:285`), MultiGCWizard (`clone_proposal_to_gcs:188`), plus new NEW HistoryLocker entries **ArchiveBatchManager** (`handleDelete:21` — cascades `import_batches` delete) and **ImportToLiveWizard** (`handleImport:388` — deletes call_log/job_work_types and inserts customers/call_log). Any authenticated sales rep can rewrite `proposals.total`, mint jobs in Schedule Command, destroy signatures, void invoices, or wipe archived batches unless RLS backstops each write. Fix: pass `teamMember` into every affected component; gate handlers on `["Admin","Manager"].includes(role) OR sales_name` match; verify RLS UPDATE/DELETE/INSERT policies exist for every listed table in `command-suite-db`.

3. **B-PublicInvoicePage-wide-select / D2 (HIGH — third audit cycle, now documented in-source).** The code comment at `src/pages/PublicInvoicePage.jsx:60-67` now explicitly acknowledges: *"BUT THIS ALLOW-LIST IS NOT THE SECURITY BOUNDARY — corrected 2026-08-10 by security review. proposal_wtc carries a TABLE-level anon SELECT grant, so a link holder can query burden_rate / markup_pct / pw_rate / materials / discount straight from PostgREST regardless of what this page selects."* Anyone with a valid viewing token — or anyone the token leaks to via forwarded email — reads full labor + material cost basis. PublicSigningPage was migrated to a SECURITY DEFINER RPC in H6/2026-05-02; the invoice page was never hardened. Fix (in `command-suite-db`): `REVOKE SELECT ON public.proposal_wtc FROM anon;` add column-scoped `GRANT SELECT (id, is_rate_card, locked_line_total, work_type_id, proposal_id, tenant_id)`; alternatively mirror H6 with `get_public_invoice_view(p_token uuid)` returning only rendered per-line values.
